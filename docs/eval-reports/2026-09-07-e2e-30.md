# T14 端到端排障评测：30 任务全量（2026-09-07）

## 1. 口径与运行环境

- **流程**（scripts/run_e2e.py）：逐任务 `reset_lab → 故障注入（核验）→ CRAG(tools=True) 排障 → LLM 判分 → reset_lab 收敛核验`；故障注入后稳定 2s；fresh thread_id；`state["host"]` 显式传入。
- **系统**：CRAG threshold=6.0、tools=True、max_rewrite=1（生成 temperature 0.2；打分 0.0；judge 0.0）；Milvus + BGEM3(bge-m3) + bge-reranker；生成/判分 SiliconFlow Qwen（72B/7D 同栈）；judge 与 agent 同 LLM 栈。
- **判分**（judge 单次调用输出 JSON）：
  - `conclusion_correct`：答案是否明确点中期望结论的关键事实（具体接口号/地址/取值）；泛泛说「配置有问题」算 false；
  - `tools_reasonable`：调用的只读工具是否足以获得该结论。**两级运行器校准**（2026-09-07 人工批准 + 修复轮 1/2 演进）：期望工具恰 1 个且恰只调用该工具 → 恒 true；多预期且调用全部 ⊆ 预期（至少一个）→ true、零调用 → false；调用含预期外工具 → 判分器按「至少一个预期工具且无越权」判据裁量。
- **计量**：CountingLLM 单题精确计数；本批 30 题 **90 次 LLM 调用**（每题恰 3 次：打分+生成+判分，0 次改写）。
- **lab 纪律**：注入/重置不 write memory（bind-mount 基线零改动）；本批 30/30 收尾重置 clean，0 handoff，0 错误，0 预算中断（无 402）；总 wall ≈ 48 min。
- 结果文件：`data/llm_cache/t14_results/agent-20260907-201609.jsonl`（逐字记录）+ `summary-*.json`。

## 5. 失败分析（逐字证据）

### 5.1 OSPF cost 抬高：0/7（最大缺口，-7）

诊断映射按人工决策走 `绕路/路径 → show_ip_route`，期望工具却是 `[get_running_config, show_ospf_neighbor]`。两类问题叠加：

1. **证据缺口（同 t02 形态）**：`show ip route` 输出里异常 cost **不显式可见**——被抬 cost 的直连网段只显示为 `C>* 10.0.12.0/30 is directly connected, eth1`，OSPF 优选绕开该链路（`O 10.0.12.0/30 [110/30] via eth2/eth3`），路由表**不出现 65535、也不点名接口 cost 配置**。归因「ethN 被配置 ip ospf cost 65535」严格需要 running-config 的 `ip ospf cost 65535` 行（同 shutdown 类需 `shutdown` 行）。
2. **judge 判 show_ip_route 越权**：7 条 judge reason 一律「未调用合理工具参考中的任何一个工具」——show_ip_route ∉ expected_tools，且其输出确实推不出配置事实，false 成立（此处的 tr=false 与 t02 修复前的误判不同，是证据真缺口）。

逐字样例（t07，core1 eth1 cost=65535）：show_ip_route 输出含
`O   10.0.12.0/30 [110/30] via 10.0.101.2, eth2 … via 10.0.102.2, eth3`、`C>* 10.0.12.0/30 is directly connected, eth1`；答案据此对照手册静态路由样例展开排查步骤，judge：`未调用合理工具参考中的任何一个工具，且未指出eth1接口被配置了ip ospf cost 65535`。
**修复方向（待人工决策，未擅动）**：cost 类元组仿 shutdown 类闭合——`("show_ip_route", "get_running_config")`，路由表给「绕路」面、running-config 给 `cost 65535` 行。

### 5.2 VLAN 标签改错：tools 6/6 但 conclusion 0/6（-6）

**证据链已闭合**（show_vlan 单工具输出同时含「原子接口失 IP + 新标签/新口」两个事实，judge 全部认可工具合理），缺口在**生成抽取**：7B/72B 模型描述了「eth1.100 没有 IPv4」却未说「地址迁到了 eth1.200/eth1.300/eth2.100/…」。逐字样例（t23，acc1 retag→200）：实况 `eth1.100 up 无 IPv4 / eth1.200 down`（铁证），答案只说「eth1.100 没有配置IPv4地址，这可能是导致网管VLAN100不通的主要原因」，judge：`Agent 未明确指出 VLAN100 地址 10.100.0.2/24 从 eth1.100 被迁到错误标签 eth1.200`。t28 同型：`仅提到 eth3.100 状态为 down`。**修复方向（待决策）**：生成侧对多实况片段加「对比陈述」引导，或换更强生成模型；非证据/映射问题。

### 5.3 judge 校准的影响（如实）

- 本批 30 题中 23 题命中运行器直判（9 题 description/no_vlan/shutdown 单期望 + 6 题 shutdown 三元组子集 + 6 题 vlan 子集 + 3 题其它），judge 只裁 conclusion；reason 带 `[多预期工具校准]`/`[单工具自动判定]` 前缀可审计。
- cost 类 7 题为「越权→裁量」场景：judge 判 tr=false 与证据缺口一致，无息噪声。

## 6. 与修复轮的归因（偏差分析）

- shutdown 6/6、no_vlan 2/2、description 9/9（17 题）= 三轮修复的直接受益面：打分门绕过（t17）、prompt 认设备实况（t02）、三元组证据闭合（t02 闭合轮）、judge 双级校准。
- 13 题失败中 7 题属 cost 类证据缺口（映射值未含 running-config）、6 题属生成抽取缺口——两者都不是本轮批准修复范围，已如实上报待决策。
- 结论：**56.7% 为当前系统真实水平**；目标 83.3% 需上述两项收口（工程上 cost 类与 t02 同构、收口把握较大；vlan 类依赖生成模型能力）。
